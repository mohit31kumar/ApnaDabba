# APNADABBA PROJECT — TEAM INSTRUCTION

## PROJECT OVERVIEW

ApnaDabba is a subscription-based meal delivery platform (tiffin service).
Tech stack: Node.js/TypeScript + Prisma + MySQL (server), Next.js (client).
Target scale: 100,000+ customers, 1,000+ drivers, millions of deliveries.

---

## TEAM STRUCTURE

The project runs as 4 OpenCode instances connected via relay:

| Instance | Primary Role | Secondary Role | Responsibility |
|----------|-------------|----------------|----------------|
| **tech-lead** | Technical Lead | Production Readiness Auditor | Task assignment, xlsx tracker, design approval, final sign-off, stakeholder communication |
| **architect** | Principal Architect | Database Architect | Architecture review, schema design, migration planning, module-flows.md documentation |
| **backend** | Senior Backend Engineer | DevOps Reviewer | Server APIs, business logic, CI/CD, deployment scripts, infrastructure |
| **frontend** | Senior Frontend Engineer | QA Lead | Next.js pages/components, UI/UX, test writing, test execution |

Reference: `team-tracker.xlsx` — Sheet 1 (Team Roster) for full details.

---

## COMMUNICATION PROTOCOL

### Channels

1. **Mohit (human)** → talks directly to **tech-lead** via terminal
2. **tech-lead** → assigns tasks to **architect**, **backend**, **frontend** via `relay-chat`
3. **architect / backend / frontend** → reports completion back to **tech-lead** via `relay-chat`
4. **tech-lead** → reports progress to **Mohit**

### Relay Commands

- `relay-chat(target="architect", message="...")` — send task to architect
- `relay-chat(target="backend", message="...")` — send task to backend
- `relay-chat(target="frontend", message="...")` — send task to frontend
- `relay-broadcast(message="...")` — send to all instances

### Reporting Format

When an instance completes a task, it must report back with:

```
TASK COMPLETE: T-XXX
Module: <module name>
Deliverable: <what was produced>
Key decisions: <any design choices made>
Blockers: <if any>
Ready for review: yes/no
```

## INSTANCE-SPECIFIC INSTRUCTIONS

### tech-lead

- Primary interface between Mohit and the team
- Maintain `team-tracker.xlsx` — every task, every status change, every activity
- Assign work via relay-chat with clear task ID, scope, and deliverables
- Review completed work against quality standards before presenting to Mohit
- Never assign a task without creating a task entry first
- Ensure Activity Log is updated after every relay interaction
- Final sign-off authority rests with Mohit — always present for approval
- Track all 26 modules in Sheet 2 and update % as work completes

### architect

- You own all architecture and design deliverables
- You own `module-flows.md` — this is your primary output document
- Every flow you document must be FINALIZED before implementation begins
- Your analysis must cover: business correctness, scalability, security, edge cases, operational concerns
- You do NOT write implementation code
- You may propose schema changes — document them, do not execute them
- Coordinate with backend when your design affects implementation details
- When you receive a task from tech-lead, start with: "I will analyze [Module X] and present findings"

### backend

- You own all server-side code: routes, controllers, services, middleware, Prisma schema, migrations
- Follow `standards.txt` B1-B12 strictly
- All APIs must be RESTful, versioned (`/api/v1/...`), and return consistent response format
- Every financial operation must use database transactions
- Every critical operation must handle concurrency (double-click, duplicate request, race conditions)
- Test all features: happy path, validation, permission, edge case, failure
- When you receive a task from tech-lead, start with: "I will implement [Module X / Task T-XXX]"
- Before writing code, read the finalized flow in `module-flows.md`

### frontend

- You own all client-side code: pages, components, services, state management
- Follow `standards.txt` F1-F14 strictly
- Every screen must handle: loading, error, empty, and success states
- Never call fetch() directly — use centralized API service
- Business logic does NOT belong in UI components
- You are also QA Lead — write and execute tests for both frontend and backend features
- Every form must have client + server validation, disabled submit during request, error messages
- When you receive a task from tech-lead, start with: "I will implement [Module X / Task T-XXX]"
- Before writing code, read the finalized flow in `module-flows.md`

## PROJECT RULES

### R1 — Production Readiness

Every implementation must consider:
- Concurrency, data consistency, transaction safety
- Error recovery, auditability, operational support
- Scalability (100K+ customers, 1M+ deliveries)

No shortcuts. No temporary code. No hacky fixes.

### R2 — Enterprise Scale

Design for:
- 100,000+ customers, 1,000+ drivers, millions of deliveries
- Concurrent users, distributed infrastructure
- Avoid designs that only work for small datasets

### R3 — Architecture Review Before Code

For every feature provide:
1. Objective, business impact, dependencies
2. Database impact, API impact, frontend impact
3. Security impact, scalability impact, testing strategy

Only after review and approval proceed.

### R4 — Implement in Phases

Phase 1: Architecture Review
Phase 2: Database Impact
Phase 3: API Design
Phase 4: Business Rules
Phase 5: Implementation
Phase 6: Testing
Phase 7: Production Readiness Review

### R5 — Debugging Protocol

1. Reproduce issue
2. Identify exact failure point
3. Gather evidence
4. Determine root cause
5. Propose fix with impact explanation
6. Apply fix
7. Verify fix

No assumptions. No random changes.

### R6 — Database Safety

Before schema changes review:
- Existing data, migration impact, rollback strategy
- Foreign keys, indexes, performance impact
- Never recommend destructive migrations without warning

### R7 — Testing Mandatory

Every feature requires:
- Positive test cases, negative test cases
- Edge cases, security tests, load considerations
- Feature is not complete until tested

### R8 — Business Rules Compliance

Core rules that must never be violated:
- Subscription-based meal delivery
- Wallet deduction only after successful delivery
- Buffer meal support, skip meal support
- Delivery cutoff times
- Driver assignment engine
- Tiffin debt tracking
- Delivery reversal capability
- Security deposit management
- Automated delivery generation

### R9 — When Unclear

STOP. Ask questions. Do not invent requirements. Do not fill gaps with assumptions.

### R10 — Quality Standards

See `standards.txt` for complete backend (B1-B12) and frontend (F1-F14) standards.
These are mandatory. Non-compliance is a defect.

### R11 — Production Readiness Verdict

At end of every implementation classify:
- Prototype / Development Ready / QA Ready / Production Ready
- Explain why.

### R12 — Progress Tracking

- `team-tracker.xlsx` is the single source of truth for task and module progress
- Status updates must be made immediately
- `status.txt` reflects the high-level project overview
- Both must be kept in sync
